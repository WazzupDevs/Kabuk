# Yayın

Üretim yayını (production kanalı, üretim projesine `db push` ya da deploy) her zaman elle ve proje sahibinindir; sırası `docs/PILOT_RELEASE.md`. Tek seferlik kurulumlar `docs/OPS.md`'de. Bölüm atıfları (ör. "Test APK'sı", "Neyi ne zaman yayınlamalı") `CLAUDE.md` → "Nerede ne var" tablosuyla bulunur.

## Neyi ne zaman yayınlamalı

`expo-updates` açık (`app.config.ts`, `updates.url` sabit). `runtimeVersion` `app.json`'daki `version`'dır (`appVersion` politikası): bir OTA güncellemesi yalnızca aynı `version`'la alınmış build'lere gider. Kanallar: `preview` build'i `preview` kanalını, `production` build'i `production` kanalını dinler.

**Kural:** native bağımlılık, config plugin ya da `app.json`/`app.config.ts`'teki native bir alan değişirse `app.json` → `version` artırılır (ör. `0.1.0` → `0.2.0`) ve yeni build alınır; aksi hâlde OTA. Artırmayı unutmak, eski APK'lara onlarda olmayan native kodu çağıran bir JS paketi gönderir ve uygulama açılışta çöker; bunu artık hiçbir şey otomatik yakalamaz (native parmak izi bırakıldı, bkz. `docs/arsiv/DECISIONS.md` → "runtimeVersion"). Kural PR şablonunda da madde olarak durur (`.github/pull_request_template.md`).

| Değişiklik                                                                                                                                                                                      | Gereken                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Yalnızca JS/TS, metin, stil, `@shared` kodu                                                                                                                                                     | `pnpm dlx eas-cli update --channel preview --message "…"` (`apps/mobile` içinde)                                                                                                                                                                                 |
| `EXPO_PUBLIC_*` değeri                                                                                                                                                                          | EAS ortam değişkenini güncelle, sonra `eas update` (değerler JS paketine girer)                                                                                                                                                                                  |
| Yeni ya da güncellenen native modül, config plugin, `app.json`/`app.config.ts` native alanı (izin, paket adı, ikon, splash, `userInterfaceStyle`), Expo SDK yükseltmesi, `google-services.json` | Önce `app.json` → `version` artır, sonra yeni `eas build --profile preview` ve APK'nın yeniden kurulması                                                                                                                                                         |
| Migration ya da `content/` (seed)                                                                                                                                                               | `pnpm supabase db push --include-seed --skip-vault`                                                                                                                                                                                                              |
| Edge Function                                                                                                                                                                                   | `pnpm supabase functions deploy <ad>`                                                                                                                                                                                                                            |
| Panel ayarı (Auth, Realtime, Storage)                                                                                                                                                           | Panelden; `config push` asla                                                                                                                                                                                                                                     |
| Eski build'leri kapatmak (zorunlu güncelleme)                                                                                                                                                   | Yeni build dağıtıldıktan sonra `pnpm supabase secrets set MIN_APP_BUILD=<yeni versionCode>`; bu build'den eski uygulamalar her fonksiyon çağrısında `update_required` alır ve "Güncelleme gerekli" ekranını gösterir. `0` ya da ayarsız: kapı kapalı değil, açık |

- dev projesi ve preview kanalı için tablodaki migration, Edge Function ve `eas update` satırlarını `DEPLOY_DEV_AUTO` açıkken main'e birleşme kendiliğinden yapar ("main'den dev projesine yayın" → "Otomatik yayın").
- Sunucu değişikliği istemciden önce yayınlanır: yeni bir alan ya da action'ı kullanan JS güncellemesi, migration ve fonksiyonlar yayında olduktan sonra gönderilir.
- Yeni native bağımlılık eklendiyse önce `version` artırılıp build alınır, sonra o build'i hedefleyen `eas update`. `version` değiştiği için eski APK'lar bu güncellemeyi almaz, yanlış koda düşmez.
- `version` artırılmadan yalnızca JS değişikliği içeren her şey (tasarım, metin, `@shared` kodu) aynı `version`'daki bütün build'lere OTA ile gider.

## Build numarası (Android versionCode) ve zorunlu güncelleme

- `apps/mobile/eas.json` → `cli.appVersionSource: "remote"`: versionCode EAS sunucusunda tutulur. `app.json`/`app.config.ts`'te versionCode yoktur (dinamik config'e yerel olarak yazılamaz; remote kaynakta yazılsa da yok sayılır).
- Android için **tek sayaç** vardır; `preview` ve `production` aynı sayacı paylaşır. İkisinde de `autoIncrement: true`: her build başlarken sayaç 1 artar ve build o sayıyı taşır. Böylece bir preview APK'sı ile bir production AAB'si hiçbir zaman aynı numarayı almaz, `MIN_APP_BUILD` ikisini de doğru ayırır. `development` profili artırmaz, o anki değeri kullanır.
- İlk değer: sayaç hiç ayarlanmadıysa ilk build'de EAS başlangıç değerini sorar ya da 1'den başlatır. Açıkça ayarlamak ya da görmek için (Expo girişi gerekir): `cd apps/mobile && pnpm dlx eas-cli build:version:set --platform android` / `pnpm dlx eas-cli build:version:get --platform android`. Sayaç geri alınmaz; Play Console da küçük versionCode'u kabul etmez.
- Uygulama bu sayıyı (`expo-application` `nativeBuildVersion`) her Edge Function çağrısında `x-app-build` header'ında gönderir; açılışta ve her öne gelişte `ping` fonksiyonunu çağırır, böylece yalnızca okuyan bir oturum (Keşfet) da kapıya takılır. `version` ("0.1.0") kullanıcıya görünen sürümdür ve OTA uyumunun anahtarıdır (`runtimeVersion`); kapı onu değil versionCode'u kullanır.
- Eski build'leri kapatmak: yeni build'in numarasını `build:version:get` ya da build sayfasından al, dağıttıktan sonra `pnpm supabase secrets set MIN_APP_BUILD=<numara>`. Ayarsız ya da `0`: kapı açık.

## main'den dev projesine yayın

Tek seferlik kurulum (yukarıda) yapılmış bir projeye main'in güncel hâlini gönderir. Repo kökünde, sırayla. `supabase login` gerekirse tarayıcıdan giriş ister; uzak veritabanına bağlanan komutlar (2–4, 6) veritabanı parolasını sorabilir (panel → Settings → Database).

1. `git checkout main && git pull && pnpm install`
2. `pnpm supabase migration list`: bağlı projeyi ve uygulanmamış migration'ları gösterir (Local dolu, Remote boş satırlar). Proje yanlışsa: `pnpm supabase link --project-ref <ref>`.
3. `pnpm supabase db push --include-seed --skip-vault --dry-run`: uygulanacakları yalnızca listeler. İçerik değiştiyse seed satırında yeni `supabase/seeds/content-<id>.sql` görünür; `(hash update)` yazıyorsa seed çalışmaz: ya dosya elle değiştirilmiştir (`pnpm seed` ile yeniden üret) ya da proje onu CRLF bir Windows kopyasından kaydetmiştir (aşağıda "Windows'ta satır sonları").
4. `pnpm supabase db push --include-seed --skip-vault`: migration'lar, ardından içerik değiştiyse yeni seed dosyası (`supabase/seeds/content-<id>.sql`; takma ad kelimeleri, kartlar, küfür listesi, mekanlar; tekrar çalıştırılabilir; silmez, ekler ya da günceller; JSON'dan çıkarılan kart deste deste `is_active = false` olur). Profil fotoğrafı kovası ve cron işleri migration'larla gelir. `--skip-vault`: `config.toml`'daki Vault sırları gönderilmez (`config.toml` yalnızca yerel ortamı tanımlar; bugün Vault bloğu yok, eklenirse yerel değer barındırılan projeye gitmez). Otomatik yayın da aynı komutu kullanır.
5. Fonksiyonların hepsi: `pnpm functions:deploy`. Liste `config.toml`'daki `[functions.*]` bloklarından okunur (şu an 18; `scripts/functions/config.test.ts` sayıyı denetler); sonda bağlı projeyi ve yayınlanan fonksiyon sayısını yazar, biri bile yayınlanamazsa sıfırdan farklı kodla çıkar. Uzun bir satırı yapıştırmak gerekmez (Windows cmd'de bölünüp fonksiyonların bir kısmı yayınlanmadan kalabiliyordu). `verify_jwt = false` her birinin `config.toml` bloğundan gelir; yeni bir fonksiyon yalnızca `config.toml` bloğu ve klasörüyle gelir, script değişmez (`scripts/functions/config.test.ts` ikisinin eşleştiğini denetler).
6. Kontrol: `pnpm supabase functions list` (18'i de `ACTIVE`, sürümleri artmış; listede başka fonksiyon yok) ve `pnpm supabase migration list` (her satırda Local ve Remote aynı). `functions deploy` repodan kalkan bir fonksiyonu barındırılan projeden **silmez**: listede `config.toml`'da olmayan bir fonksiyon varsa elle silinir. Adım 23.4a'dan sonra bir kez `reveal` için (dev ve üretim projesinde ayrı ayrı):
   1. `pnpm supabase migration list`: bağlı proje doğru mu (yanlışsa `pnpm supabase link --project-ref <ref>`).
   2. `pnpm supabase functions delete reveal`
   3. `pnpm supabase functions list`: 18 fonksiyon, `reveal` yok.
7. Sırlar, yalnızca gerektiğinde (`pnpm supabase secrets list` ile bak):
   - `MIN_APP_BUILD`: yalnızca eski build'leri kapatırken (bkz. "Build numarası").
   - `POSTHOG_PERSONAL_API_KEY`, `POSTHOG_PROJECT_ID`, isteğe bağlı `POSTHOG_HOST`: hesap silmede PostHog kişi silme; yoksa atlanır.
   - `SMS_PROVIDER`, `NETGSM_USERCODE`, `NETGSM_PASSWORD`, `NETGSM_HEADER`, `SEND_SMS_HOOK_SECRETS`: yalnızca pilot (üretim) projesinde, Netgsm kancası için (Send SMS Hook; panel adımları sırasıyla `docs/SPEC_V3.md` §2.3). Dev projesinde tanımlanmaz ve kanca kapalıdır: orada SMS yoktur, giriş test numaralarıyladır.
8. Panel: Realtime → Settings → **Allow public access kapalı** (değişmedi, kontrol et). Bu sürüm yeni bir panel ayarı istemez.
9. Sonra istemci: native değişiklik varsa yeni `eas build`, yoksa `eas update` (bkz. "Neyi ne zaman yayınlamalı").

- Asla: `supabase config push`, `supabase/local/secrets.sql`'i barındırılan projede çalıştırmak, secret key'i bir dosyaya yazmak.

**Otomatik yayın (`.github/workflows/deploy-dev.yml`).** Repo değişkeni `DEPLOY_DEV_AUTO` `true` iken main'e her birleşmeden sonra, main'deki `ci` geçince 4., 5. ve 9. adım kendiliğinden çalışır: migration ve seed (`db push --include-seed --skip-vault`), fonksiyonlar (`pnpm functions:deploy`), sonra preview kanalına OTA (`eas update --channel preview --environment preview`). Her adım yalnızca dosyaları son başarılı yayından beri değiştiyse çalışır (`scripts/deploy/plan.ts`): `supabase/migrations/` ya da `seeds/`; `supabase/functions/` ya da `config.toml`; OTA için `apps/mobile/` ya da `_shared/pure/`. Başarısız bir adım sonraki birleşmede yeniden denenir. 6. adımın `migration list` denetimi de koşuda: `db push`'tan sonra her satırda Local ve Remote aynı değilse fonksiyonlar ve OTA gitmez, koşu kırmızı biter. Koşu ayrıca projede olup `config.toml`'da olmayan fonksiyonları özetine uyarı olarak yazar (`scripts/deploy/cli.ts check-functions`); hiçbir şey silmez ve koşuyu düşürmez, silmek 6. adımdaki elle adımdır. Yukarıdaki elle sıra üretim projesi ve otomatik yayın kapalıyken geçerli kalır; production kanalı her zaman elle.

- Yalnızca dev projesi: ref `_shared/pure/devProject.ts`'ten gelir ve `link`'ten sonra denetlenir; OTA, EAS `preview` ortamındaki `EXPO_PUBLIC_SUPABASE_URL` dev projesinin adresi değilse gönderilmez (değişken `plaintext` olmalı, bkz. "Test APK'sı" adım 3). Üretim ref'i repoda yoktur, girdiyle verilemez.
- Native dosya (`app.json`, `app.config.ts`, `assets/icon/`, `package.json` → `dependencies`) `version` artmadan değiştiyse sunucu yayınlanır, OTA bekletilir ve koşu kırmızı biter. Native ise `version` artır ve build al; yalnızca JS ise Actions → deploy-dev → Run workflow (`dry_run` kapalı, `force_ota` açık).
- Kurulum (tek seferlik, repo sahibi): GitHub → Settings → Environments → New environment `dev` → Deployment branches and tags: Selected branches and tags → `main`. Environment secrets: `SUPABASE_ACCESS_TOKEN` (Supabase → Account → Access Tokens), `SUPABASE_DB_PASSWORD` (dev projesinin veritabanı parolası), `EXPO_TOKEN` (expo.dev → Account settings → Access tokens). Sonra Actions → deploy-dev → Run workflow (main, `dry_run` açık): bağlanır, uygulanacak migration'ları ve fonksiyonları listeler, preview ortamının adresini denetler, hiçbir şey yayınlamaz; çıktısı koşunun özet sayfasında. Yeşilse Settings → Secrets and variables → Actions → **Variables** → New repository variable: `DEPLOY_DEV_AUTO` = `true` (ortam değişkeni değil: işin `if`'i yalnızca repo değişkenini okur). Değişken yokken birleşme hiçbir şey yayınlamaz, koşu "skipped" biter.
- Durdurmak: `DEPLOY_DEV_AUTO` değişkenini sil ya da `false` yap; elle koşu çalışmaya devam eder. Hepsini kapatmak: Actions → deploy-dev → ⋯ → Disable workflow. Elle koşu seçenekleri: `dry_run` (yalnızca kontrol), `everything` (son yayına bakmadan hepsi), `force_ota`.
